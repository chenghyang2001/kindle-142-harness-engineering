### 3. 交接提升 vs 直接寫入

`handoff_promotion`：`candidate_source: worker-analysis` → `promoter: supervisor-policy` → `promoted_record_id: mem_d013e28edf43aca4`（內容：做安全審查交接時，先摘要持久證據再給建議）。

| | 直接寫入 | 交接提升 |
| --- | --- | --- |
| 誰寫 | 產生想法的那個代理自己寫 | worker 只提出**候選**，由另一方（supervisor-policy）審過後才寫 |
| 信任等級 | 等於寫入者自己的等級 | 由提升者決定（這裡是 trusted_tool），來源記為 `worker-analysis-promoted-by-supervisor` |
| 風險 | 一個代理讀到被投毒的上下文，就能直接把毒寫進長期記憶 | 中間多一道審查，worker 的上下文被污染時，毒不會自動變成長期規則 |
| 證據 | 只知道是誰寫的 | 知道是誰提的、誰核准的，帳本能追到兩方 |

簡單說：直接寫入是「我覺得對，我就記下來」；交接提升是「我建議記下來，由上級決定要不要成為以後的規則」。在這個實驗室裡，提升是用 `propose_write` 搭配較高的信任等級與標明提升者的 source 來模擬，並沒有獨立的審查函式；正式系統中，這一步應該是一個真正的審查關卡。

### 4. 為什麼回滾用墓碑而不是直接刪除？

`core.py` 的 `MemoryFirewall.rollback` 只把記錄標成 `deleted=True` 並寫上 `tombstone_reason`，記錄本身留在帳本；`read()` 會跳過有墓碑的記錄，所以代理讀不到（`rollback_read_count: 0`）。

**對稽核的好處：**

- 事後能回答「這條規則曾經存在嗎？存在多久？為什麼被撤？」。如果直接刪掉，`triage.shortcut` 曾經讓 beta 事故被丟進低關注佇列這件事，就沒有任何紀錄可以解釋當時的決策。
- 墓碑原因（`overgeneralized from one incident; require more evidence before reuse`）本身就是教訓：記錄的是「為什麼這種記憶不可信」，下一次看到類似的候選，就知道要多要證據。
- 帳本保持只增不減，比較難被人悄悄竄改歷史。

**對「防止毒化記憶復活」的好處（設計上）：**

- 有墓碑，系統才「記得自己拒絕過這條」。同樣的內容之後再被提出（例如另一個被污染的代理又學到同一條捷徑），可以比對墓碑直接拒絕；如果已經刪乾淨，系統對它毫無印象，它就能重新寫進來。
- record_id 是由 key＋value＋租戶算出來的雜湊，所以同樣內容會得到同一個 ID，天然適合拿來比對墓碑。

**照實記錄：這個實驗室的實作還沒做到上面那一點。** 我在 scratchpad 用 `MemoryFirewall` 做了一個小實驗（沒有修改原始碼）：寫入 `triage.shortcut` → 回滾 → 讀取筆數 0 → **用完全相同的內容再寫一次** → 得到同一個 `mem_e3b1b8cf8b6d6169` 和 `stored`，讀取筆數變回 1。原因是 `propose_write` 直接用新的記錄覆蓋同一個 ID，`deleted` 被重設為 False，墓碑和原因一起消失了。也就是說，**墓碑在這裡保住了稽核紀錄，卻還沒擋住復活**；正式系統需要在 `propose_write` 開頭檢查「這個 ID 或這段內容是否已有墓碑」，有的話就拒絕或要求更高層級核准。
