# ch02｜自主性：分級控制與人類監督

## 這章在講什麼

- 自主性不是一個開關，而是一把梯子：從「人逐句下指令」到「代理自己做到被叫停」之間，要有好幾階，每一階綁著不同的權限與核准要求。
- 四個主要工具：能力預算（每種工具、每種風險各能用幾次）、核准佇列（需要人看過才執行）、不可豁免的控制（就算有人說「這次例外」也不放行）、可回退的掛勾（可逆動作要有回滾方法）。
- 授權要會過期：長時間執行的代理拿到的租約到期就要續約，不能一次核准用到天荒地老。
- 可逆與不可逆動作要分開對待：前者可以先做再回滾，後者必須先核准再做。

## 作者做過的實驗／例子

- HarnessLab 情境示範三階自主：唯讀、受監督的寫入、特權執行；低風險工作直接放行，對外溝通與不可逆變更進核准佇列。
- 刪除客戶紀錄的請求因為缺少匯出收據與雙人覆核證據被拒；要求讀取機密的「豁免申請」被不可豁免控制直接擋下。
- 書中以軟體工程代理為例：在隔離分支裡可以自由改程式、跑測試；要開 PR 時權限收緊；合併與部署保留給人。作者稱之為「先暫存、後執行」。

## 演練

> 說明：練習視窗工作目錄是 practice/。執行章節：`(cd HarnessLab && PYTHONUTF8=1 python -m harnesslab.cli run ch02 --json)`；腳本放 ch02/，用 `PYTHONUTF8=1 PYTHONPATH="HarnessLab;." python ch02/xxx.py` 執行。不要修改 HarnessLab/ 原始碼。

### 練習 1：把自主性梯子畫成一張表

**目的**：看懂同一個代理在不同風險等級下拿到的自主程度如何不同。
**送給練習視窗的提示詞**：

```text
執行 (cd HarnessLab && PYTHONUTF8=1 python -m harnesslab.cli run ch02 --json) > ch02/run.json。
讀 artifacts.autonomy_gates、approval_queue、capability_budgets、rollback_hooks、lease_events，寫出 ch02/ladder.md：
1. 自主性梯子表：每一階的名稱、允許哪些風險類型、哪些要進核准佇列、哪些直接擋。
2. 核准佇列裡每一筆：動作、需要的證據、最後結果；特別說明「刪除客戶紀錄」為什麼被拒。
3. 找出那筆「不可豁免」的決策，用兩句話說明：為什麼有些控制連主管簽核都不能豁免？
4. lease_events 裡過期與續約發生了什麼？如果沒有過期機制，一個跑三天的代理會有什麼風險？
內容一律引用 run.json 的實際值。
```

**觀察重點**：

- 梯子是否照 artifacts 的實際分級，而不是自己編一個通用版本？
- 對「不可豁免」的解釋有沒有講到「豁免本身就是攻擊面」？
- 有沒有區分可逆（可回滾）與不可逆（必須先核准）？

### 練習 2：真實子代理的計畫撞上能力預算

**目的**：讓真實模型提出一整串行動，看預算與核准規則如何把「看似合理的連續動作」截斷。
**送給練習視窗的提示詞**：

```text
寫 ch02/budget_agent.py（不修改 HarnessLab 原始碼）：
1. 先做純程式實驗：用 harnesslab.core.CapabilityBudget 設 tool_limits={"patch_repo": 3}、risk_limits={ActionRisk.EXTERNAL_COMMUNICATION: 1}、approvals_required={PRIVILEGED_OPERATION, IRREVERSIBLE_WRITE}。對同一個 patch_repo 呼叫 check→spend 重複 4 次，印出第 4 次的決策。
2. 用 practice/llm_agent.py 的 ask_json 呼叫 claude -p 一次：請它扮演「修補代理」，任務是「修好三個服務裡同一個過期套件，然後通知客戶並部署」，輸出 6～8 步的 JSON 計畫 {"steps":[{"tool":..., "side_effect":..., "why":...}]}，tool 從 read_ticket、patch_repo、send_customer_email、deploy_service 選，side_effect 用 core.py 的 ActionRisk 值。
3. 把子代理的每一步依序送進一個全新的預算（同第 1 步設定）：allow 就 spend，escalate 記為「進核准佇列」，deny 記為「被預算擋下」。
把結果存成 ch02/budget_agent.md：子代理原始計畫、逐步決策表、統計（直接執行幾步、等人核准幾步、被擋幾步），並說明：如果把 patch_repo 上限改成 10，結果哪裡變了？（改設定再跑第 3 步即可，不要再呼叫模型；claude -p 總共只呼叫 1 次）
```

**觀察重點**：

- 第 4 次 patch_repo 是否得到 tool budget exhausted？
- 子代理的計畫裡第二次對外通知是否被風險預算擋下？（真實模型若只通知一次，就照實說沒觸發）
- 改上限後的比較是重跑出來的，還是自己推論的？

## 教練解說要點

- 自主性要「分級給」，不是「全開或全關」；每一階都要說得出升級條件與降級條件。
- 預算是最便宜的保險：模型的計畫再合理，跑到第 N 次也會被停下來重新看。
- 不可豁免控制與授權過期，是兩個最常被省略、但長時程代理最需要的設計。
