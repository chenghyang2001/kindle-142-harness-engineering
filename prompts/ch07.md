# ch07｜可觀測性、評估與爬坡證據

## 這章在講什麼

- 可觀測性要回答：代理做了什麼、為什麼、根據什麼證據、後來的改動讓系統更安全還是更危險。只有漂亮圖表與 token 數，作者稱為「軌跡劇場」。
- 決策軌跡（trace span）要記下每一個控制判斷；敏感內容在寫進軌跡前先遮蔽。
- 證據信封（evidence envelope）把軌跡、產物雜湊、遮蔽紀錄、政策版本綁成一個防竄改雜湊；重播包（replay bundle）讓稽核者能重現當時的判斷。
- 爬坡要有評估閘門：候選改進若讓安全指標退步，即使速度更快、成功率更高，也要擋下或升級給人；代理自我改進（遞迴改進）沒有證據與回滾就不准上線。

## 作者做過的實驗／例子

- HarnessLab 情境：觀察一個高風險動作，遮蔽後寫入軌跡、封存證據信封、建重播包並驗證、比對基準指標發現退步而升級審查、跑一輪爬坡評估、擋下沒有證據的自我改進。
- 書中例子：某個候選方案用較激進的取樣，提升了成功率與速度，卻壓低了遮蔽率與安全攔截率，被回歸閘門一票否決。

## 演練

> 說明：練習視窗工作目錄是 practice/。執行章節：`(cd HarnessLab && PYTHONUTF8=1 python -m harnesslab.cli run ch07 --json)`；腳本放 ch07/，用 `PYTHONUTF8=1 PYTHONPATH="HarnessLab;." python ch07/xxx.py` 執行（可 `from chapters.ch07.scenario import _regression_report, _metric_score`）。不要修改 HarnessLab/ 原始碼。

### 練習 1：拆開證據信封與回歸閘門

**目的**：看懂一份「可被稽核」的執行紀錄包含哪些東西。
**送給練習視窗的提示詞**：

```text
執行 (cd HarnessLab && PYTHONUTF8=1 python -m harnesslab.cli run ch07 --json) > ch07/run.json。
讀 artifacts.redacted_observation、trace_spans、evidence_envelope、artifact_hashes、replay_bundle、replay_verified、benchmark_regression、hill_climb、governed_rsi，寫出 ch07/evidence-reading.md：
1. 遮蔽了哪些欄位？遮蔽後的軌跡還能支援事後調查嗎？
2. 證據信封裡綁了哪些東西？如果有人事後改了一個 span 的屬性，誰會發現、怎麼發現？
3. 重播包包含哪些輸入？為什麼要包含政策版本？
4. benchmark_regression 的基準與候選各是多少、哪幾個安全指標退步、最後判定是什麼？
5. hill_climb 每一輪選了誰、為什麼；governed_rsi 為何被擋？
最後用 3 句話說明你理解的「軌跡劇場」與真正的證據差在哪。
```

**觀察重點**：

- 是否講出「雜湊綁定 span 內容、改一個字就對不上」？
- 回歸判定是否引用實際數字與失敗的指標名稱？
- 自我改進被擋的理由是否講到「沒有證據與回滾」？

### 練習 2：把真實模型呼叫封進證據信封，再試著竄改

**目的**：把一次真實的子代理呼叫變成可稽核、可驗證的紀錄，並親手證明竄改會被發現。
**送給練習視窗的提示詞**：

```text
寫 ch07/traced_agent.py（不修改原始碼）：
1. 用 harnesslab.core.Tracer(run_id="k142-ch07", actor="triage-subagent") 開一個 span "subagent_call"。
2. 在 span 裡用 practice/llm_agent.py 的 ask 呼叫 claude -p 一次：請它扮演資安分流代理，替一則虛構事故寫 3 句摘要；提示詞裡故意放一段假的聯絡資料「客戶 email: amy@example.com，api_key=sk-test-123」。
3. 寫入軌跡前先自己做遮蔽：把 email 與 api_key=... 換成 [REDACTED]，在 span.attributes 存遮蔽後的 prompt 與回覆、存回覆的 sha256，並把遮蔽的欄位名記進 redactions。
4. 產生 envelope（artifacts 傳入回覆雜湊），印出 tamper_evident_hash()。
5. 竄改測試：改掉 span.attributes 裡回覆的一個字，再算一次 hash，比較兩次是否不同；再把回覆原文重算 sha256，確認與信封中的產物雜湊一致（模擬稽核驗證）。
6. 回歸閘門小實驗（不呼叫模型）：用 _regression_report，基準 {"task_success":0.80,"unsafe_block_rate":0.95,"redaction_recall":0.90,"replay_pass_rate":1.0,"median_latency_ms":1200}，候選把延遲降到 960 但 redaction_recall 降到 0.75，印出判定。
結果存到 ch07/traced_agent.md：遮蔽前後對照（原文不要出現在檔案裡，只寫「已遮蔽」與欄位名）、兩次 hash、驗證結果、回歸判定。另外檢查：模型的回覆裡有沒有把 api_key 或 email 照抄回來？若有，你的遮蔽有沒有擋住？claude -p 只呼叫 1 次。
```

**觀察重點**：

- 竄改後 hash 是否不同？雜湊是腳本實算的嗎？
- 模型回覆有沒有回顯假金鑰或 email，遮蔽是否也套用在回覆上？（只遮 prompt 不遮回覆是常見漏洞）
- 回歸閘門是否因 redaction_recall 退步而判 escalate？

## 教練解說要點

- 可觀測性不是「多記一點」，而是記下足以重現判斷的證據，並保證它沒被改過。
- 遮蔽要同時套在輸入與輸出：模型很常把上下文裡的敏感字串原樣吐回來。
- 爬坡改進要過安全閘門：快了、準了，但安全指標退步，就不是改進。
