# ch08｜執行期操控：介入、政策注入與安全回滾

## 這章在講什麼

- 前幾章是在出發前把代理設定好；本章處理已經在跑的代理。長時程執行中世界會變：票券多了惡意留言、發現工具分類錯誤、新政策在任務半途發布。
- 介入要有分級的動詞：觀察、警示、暫停、阻擋、終止、隔離、恢復，像電力系統的斷路器那樣逐級升高。
- 介入要保留證據：暫停前先存檢查點與事件帳本，恢復時才知道從哪裡接、重播時才知道發生過什麼。
- 臨時政策要有期限（policy overlay with expiry）；已經做下去的可逆動作，用補償（compensation）回滾，而不是假裝沒發生。

## 作者做過的實驗／例子

- HarnessLab 情境是一次事故處理：讀票券 → 發現惡意上下文並隔離 → 寫可逆草稿 → 暫停 → 注入臨時政策 → 擋下含個資的客戶信 → 終止一直重試的子任務 → 從檢查點恢復 → 重播證據 → 補償回滾草稿 → 臨時政策到期 → 最終檢查點。
- 書中情境：突發詐騙事件時，主管即時注入新政策，讓正在處理退款的客服代理立刻暫停高風險類別退款，且不會重複撥款。

## 演練

### 練習 1：把一次介入整理成時間線

**目的**：看清楚七個操控動詞在一次執行中依序出現的樣子。
**送給練習視窗的提示詞**：

```text
執行 (cd HarnessLab && PYTHONUTF8=1 python -m harnesslab.cli run ch08 --json) > ch08/run.json。
讀 decisions 與 artifacts（checkpoint_ids、resumed_from_step、final_step、quarantined_contexts、blocked_tools、killed_subruns、policy_overlay、memory_rollback、evidence、replay），寫出 ch08/steering-timeline.md：
1. 時間線表：步驟、動作（observe／warn／pause／block／kill／quarantine／recover／compensate）、觸發原因、留下的證據。
2. 臨時政策 overlay 的內容與期限是怎麼定義的？讀 HarnessLab/chapters/ch08/scenario.py 的 _overlay_active，說明它用什麼判斷到期。
3. 為什麼對重試的子任務用 kill，而不是一直 block？
4. 補償回滾復原了什麼？為什麼比「刪掉草稿」好？
```

**觀察重點**：

- 時間線順序是否與 decisions 一致？
- 是否注意到 overlay 的到期在情境中是用「步數」判斷（expires_after_step），而 core.py 的 inject_policy 記的是秒數 expires_at？
- kill 的理由是否講到「無限重試本身就是風險」？

### 練習 2：真實退款代理跑到一半，主管注入臨時政策

**目的**：用真實模型產生一串退款動作，在半途注入有期限的政策，看執行期操控如何改變後半段的結果。
**送給練習視窗的提示詞**：

```text
寫 ch08/refund_steering.py（不修改原始碼）：
1. 用 practice/llm_agent.py 的 ask_json 呼叫 claude -p 一次：請它扮演客服退款代理，處理 6 筆虛構退款（自己編：訂單號、金額、類別，其中至少 2 筆類別為 "gift_card"），輸出 {"refunds":[{"order":..., "amount":..., "category":..., "action":"refund"}]}。
2. 用 harnesslab.core.RuntimeController 逐筆執行（只是模擬，記在 list 裡）：第 1 筆前先 checkpoint；處理完第 2 筆後呼叫 pause("fraud alert")，再 inject_policy(run_id, {"block_categories":["gift_card"], "expires_after_step": 5}, ttl_seconds=60)，然後 resume_from 檢查點之後的狀態繼續。
3. 自己寫 overlay_active(step) 函式（仿照 chapters/ch08/scenario.py 的 _overlay_active 用步數判斷），第 3～5 筆若 overlay 生效且類別在 block_categories 就 block，第 6 筆以後 overlay 到期恢復正常。
4. 加一個「冪等」保護：已退款的訂單號若再出現就跳過，證明恢復後不會重複撥款（可以故意把第 2 筆在恢復後重送一次測試）。
5. 再測一次 ttl：另外 inject_policy(..., ttl_seconds=0)，印出 expires_at 與 time.time() 的比較，說明 core.py 本身有沒有任何地方會自動檢查 expires_at。
結果存到 ch08/refund_steering.md：子代理原始退款清單、逐筆結果表（步數、執行／阻擋／跳過、原因）、重複撥款測試結果、ttl 觀察。claude -p 只呼叫 1 次。
```

**觀察重點**：

- 第 3～5 筆的 gift_card 是否被擋、第 6 筆以後是否恢復？（若子代理把 gift_card 排在別的位置，結果會不同，照實記錄）
- 重送的第 2 筆是否被冪等保護跳過？
- 是否發現 core 的 inject_policy 只記期限、沒有人去檢查：期限要由 harness 在每一步主動判斷？

## 教練解說要點

- 執行期操控的關鍵是「分級」與「留證據」：先觀察、再警示，必要時暫停或終止，每一步都要能重播。
- 臨時政策一定要有期限，否則緊急措施會悄悄變成永久規則；期限也要有人真的去檢查。
- 恢復之後最怕重複執行有副作用的動作，冪等鍵是最簡單有效的保護。
