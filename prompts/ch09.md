# ch09｜擴展性：代理群協調不連鎖崩潰

## 這章在講什麼

- 單一代理在 demo 裡看起來很安全，因為只有一個使用者、一個任務、一條順利路徑。正式的代理群有很多租戶、工作者、佇列、重試、變動的流量限制，以及在工作進行中突然發生的局部故障。
- 代理群的協調本身就是安全控制：決定哪些工作能開始、哪些要等、哪個工作者能持有租約、哪些重試是安全的、哪些容量已經被承諾。
- 主要工具：租戶隔艙（bulkhead，像船的水密艙）、全域並行上限與反壓（back-pressure）、容量配額、流量窗口、冪等鍵、隔離被入侵的工作者、依時段（epoch）分配長時間工作的容量。

## 作者做過的實驗／例子

- HarnessLab 情境有兩個租戶（acme、globex）：工作進各自的隔艙，全域滿載時排隊、acme 超出配額時升級、流量窗口用完延到下一窗；一個工作者被判定遭入侵，租約撤銷並重新排隊，重試靠冪等鍵不重複副作用；同一個冪等鍵卻帶不同內容的請求被擋。
- 書中情境：警報分析系統遇到雜訊規則瞬間產生數百個事件，各子代理同時狂呼叫資安工具，控制平面啟動隔艙與反壓，避免整個代理群雪崩。

## 演練

> 說明：練習視窗工作目錄是 practice/。執行章節：`(cd HarnessLab && PYTHONUTF8=1 python -m harnesslab.cli run ch09 --json)`；腳本放 ch09/，用 `PYTHONUTF8=1 PYTHONPATH="HarnessLab;." python ch09/xxx.py` 執行（可 `from chapters.ch09.scenario import IdempotencyLedger, WorkItem`）。不要修改 HarnessLab/ 原始碼。

### 練習 1：讀懂代理群的狀態

**目的**：看懂隔艙、佇列、配額、冪等帳本在 JSON 裡的樣子。
**送給練習視窗的提示詞**：

```text
執行 (cd HarnessLab && PYTHONUTF8=1 python -m harnesslab.cli run ch09 --json) > ch09/run.json。
讀 artifacts.fleet、idempotency_ledger、rate_limits、capacity_governance、controls_exercised、required_controls、unsafe_paths，寫出 ch09/fleet-reading.md：
1. 兩個租戶各自的隔艙上限、排隊的工作、被升級的工作。
2. 被入侵的工作者發生了什麼：租約怎麼處理、工作怎麼重新排隊、重試為什麼不會重複副作用？
3. 冪等帳本的每一筆狀態；「同一把鑰匙、不同內容」為什麼要擋？
4. required_controls 是否都出現在 controls_exercised？列出比對結果。
5. 對照 HarnessLab/chapters/ch09/README.md 的 Production Review Checklist，挑三項說明這個情境怎麼滿足它。
```

**觀察重點**：

- 是否區分「全域滿載的排隊」與「租戶隔艙滿的排隊」？
- 冪等的解釋是否講到「重送同樣內容＝安全重播；同鑰匙不同內容＝可能是攻擊」？
- required_controls 的比對是程式算的還是目測？

### 練習 2：讓真實子代理當工作者，在隔艙與冪等保護下執行

**目的**：把真實模型呼叫當成代理群裡的工作，看吵鬧的鄰居不會拖垮別的租戶，失敗重試也不會重複執行。
**送給練習視窗的提示詞**：

```text
寫 ch09/fleet_agents.py（不修改原始碼）：
1. 吵鬧鄰居實驗（不呼叫模型）：harnesslab.core.FleetCoordinator(concurrency_limit=4, per_tenant_quota=2)，acme 連送 5 個工作、globex 送 2 個，印出每一筆決策；再把 per_tenant_quota 拿掉（設成 99）重跑，比較 globex 的工作是否被 acme 擠到排隊。
2. 真實工作者（最多呼叫 claude -p 3 次）：建一個 IdempotencyLedger(retry_limit=2)，準備 3 個 WorkItem（自己填欄位，tenant 分屬 acme／globex，payload 是要模型做的小任務，例如「用一句話分類這則警報的嚴重度：…」）。工作先 FleetCoordinator.submit 獲准，再 ledger.start；只有 start 回 ALLOW 的才用 practice/llm_agent.py 的 ask 真的呼叫模型，成功後 ledger.complete 並 fleet.complete。
3. 重試測試：把第 1 個 WorkItem 原封不動再送一次 ledger.start（應回放已完成結果、不再呼叫模型）；再做一個同 idempotency_key 但 payload 不同的 WorkItem（應被擋）。
結果存到 ch09/fleet_agents.md：吵鬧鄰居兩種設定的對照表、3 個真實工作的模型回覆、重試與冒用鑰匙的決策，以及實際呼叫模型的次數（必須 ≤3，請在腳本裡計數並印出）。
```

**觀察重點**：

- 有配額時 globex 是否照樣被放行；拿掉配額後是否被 acme 擠到排隊？
- 重送完成的工作是否沒有再呼叫模型？模型呼叫次數是否 ≤3 且有計數證明？
- 同鑰匙不同內容是否被 deny？

## 教練解說要點

- 規模一大，「誰先誰後」就是安全問題：沒有隔艙，一個租戶的暴衝會變成全體的停擺。
- 反壓不是失敗，是控制平面在說「慢一點」；升級是在說「這要人決定」。
- 冪等鍵讓重試變安全，也讓「同鑰匙換內容」的冒用無所遁形。
